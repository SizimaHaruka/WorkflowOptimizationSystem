# 合理化検討ワークフロー 軽量Webシステム検討

作成日: 2026-07-15

## 1. 結論

`workflow` 配下の標準フローと帳票を、案件単位で入力・確認・追跡できる軽量な ASP.NET Core Razor Pages アプリとして実装する方針がよい。

なお、このワークフローはまだ実運用前であり、運用しながら手順、帳票項目、ステータス、ゲート条件が大きく変わる前提で扱う。初期開発では、仕様変更を抑え込むよりも、変更しやすい構造で早く試し、手戻りや一部バグを許容しながら改善する。

現行運用中の `参考` システムは、認証、Razor Pages の画面構成、EF Core / SQL Server、共通レイアウト、デプロイ手順の参考として使う。一方で、工数・時間外・帳票・CSV・承認ルートなどの業務機能は今回の目的に対して重いため、丸ごと移植しない。

最初のMVPは、次の4点に集中する。

1. 案件台帳を作る。
2. F01からF11の帳票内容を案件に紐付けて記録する。
3. G0からG6のゲート判定とステータス遷移を管理する。
4. 作業、問題、改善案、要求事項、意思決定、課題を相互追跡できるようにする。

## 2. 対象ワークフロー

標準フローは次の通り。

```text
案件受付
→ 事前調査・対象範囲設定
→ As-Isヒアリング
→ 現状業務フロー作成
→ 問題分析
→ 改善案立案
→ 効果・実現性評価
→ To-Be設計
→ 要求事項化・実施判断
→ 実施後評価
```

ステータスは `workflow/01_運用規程.md` の定義を採用する。

```text
受付
→ 事前確認中
→ 調査中
→ As-Is確認中
→ 改善案検討中
→ 評価中
→ To-Be検討及び確認中
→ 実施判断待ち
→ 実施中
→ 効果確認中
→ 完了
```

補助ステータスとして、保留、中止、差戻しを持つ。

ゲートは G0 から G6 を採用し、各ゲートで完了条件チェック、判断者、判断日、コメントを残す。

## 3. 画面構成

### 3.1 初期画面

- 要対応ダッシュボード
- 自分が担当する案件
- 期限超過の課題・宿題
- ゲート判断待ちの案件
- ステータス別件数

### 3.2 案件管理

- 案件一覧
- 案件新規登録
- 案件詳細
- ステータス変更
- ゲート判定
- 添付資料管理

案件詳細は、上部に案件の基本情報、現在ステータス、次に行う作業を表示し、下部をフェーズ別タブにする。

### 3.3 フェーズ別入力

- F01 案件受付票
- F02 調査計画票
- F03 作業ヒアリング票
- F04 業務フロー整理票
- F05 問題・課題一覧
- F06 改善案評価票
- F07 To-Be作業定義票
- F08 要求事項一覧
- F09 効果確認票

F10 課題・宿題管理表と F11 意思決定記録は、全フェーズから参照・追加できる共通機能として扱う。

### 3.4 追跡ビュー

要求事項が、どの作業、問題、改善案、To-Be作業から来ているかを一覧で確認する。

最低限、次の対応関係を見られるようにする。

- As-Is作業 -> 問題
- 問題 -> 改善案
- 改善案 -> To-Be作業
- To-Be作業 -> 要求事項
- 要求事項 -> 実施判断
- 問題・要求事項 -> 効果確認

## 4. データ設計方針

軽量化のため、初期実装では「主要項目は列、帳票詳細はJSON」のハイブリッド構成にする。

帳票ごとに完全な正規化テーブルを作ると、初期開発量と変更コストが大きくなる。まずは検索・一覧・追跡に必要な項目だけを列として持ち、フォーム固有項目は `ContentJson` に保存する。運用後に検索頻度が高い項目だけ列へ昇格する。

実運用前の探索段階では、フォーム項目や選択肢の変更が頻発する可能性が高いため、初期MVPでは過度な制約、複雑な承認制御、厳密すぎる正規化を避ける。代わりに、案件番号、ステータス、担当、期限、ゲート判定、追跡リンクなど、後から整理しにくい骨格だけを先に固める。

### 4.1 中心テーブル

|テーブル|用途|
|---|---|
|Cases|案件台帳。案件番号、案件名、部署、依頼者、責任者、ステータス、優先度など|
|CaseForms|F01からF09のフォーム本文。フォーム種別、版、状態、JSON本文、確認者など|
|WorkItems|As-Is作業、To-Be作業、フロー上の作業単位|
|Problems|問題・課題。分類、現象、影響、原因仮説、重要度など|
|ImprovementOptions|改善案。方針、効果、費用、リスク、推奨度など|
|Requirements|要求事項。分類、優先度、受入条件、対応方式、状態など|
|ActionItems|課題・宿題。担当、期限、状態、回答・処置など|
|DecisionRecords|意思決定記録。決定事項、根拠、影響、承認など|
|GateReviews|G0からG6の判定履歴|
|TraceLinks|作業・問題・改善案・要求事項間の追跡リンク|
|Attachments|案件添付ファイル|
|Users|利用者、ロール|

### 4.2 案件ステータス

ステータスは文字列定数で管理し、表示名はアプリケーション層で解決する。

初期実装では、ステータス変更時に次を記録する。

- 変更前ステータス
- 変更後ステータス
- 変更者
- 変更日時
- コメント
- 差戻し、保留、中止の場合の理由

### 4.3 版管理

帳票は `CaseForms.Version` を持つ。

MVPでは、編集のたびに完全な履歴を取るのではなく、次のイベントで版を上げる。

- ゲート承認
- 差戻し後の再確認
- 実施判断
- 案件終結

必要になれば、`CaseFormHistories` を追加して保存時点ごとのスナップショットを保持する。

## 5. 参考システムから流用するもの

`参考` は .NET 10 / ASP.NET Core Razor Pages / SQL Server / IIS を前提とした現行システムであり、次を流用候補にする。

|流用候補|方針|
|---|---|
|Razor Pages 構成|画面単位の `.cshtml` と `PageModel` の分け方を踏襲する|
|共通レイアウト|ナビゲーション、ログインユーザー表示、Bootstrap ベースの画面枠を参考にする|
|認証|Cookie認証、DBログイン、Windows認証併用の考え方を流用する|
|EF Core|DbContext、Entity Configuration、SQL Server 接続の構成を参考にする|
|入力エラー表示|画面エラーと項目単位ハイライトの方針を使う|
|CSV出力補助|将来、一覧エクスポートを作る場合に参考にする|
|デプロイスクリプト|IIS配備、staging、世代保存、切戻しの考え方を流用する|
|標準実装ルール|submit button、EF Core LINQ、ダウンロード処理の注意点を採用する|

## 6. 流用しないもの

次は今回の軽量システムでは初期導入しない。

- 工数入力、時間外申請、締め、帳票、CSV自動出力の業務機能
- QuestPDF による固定帳票生成
- バックグラウンド定時出力サービス
- 複雑な承認ルートマスタ
- 外部勤務予定、組織、承認情報の同期
- 電子印影、承認コード確認

ただし、将来「要求事項一覧」「意思決定記録」「効果確認票」を正式帳票としてPDF化したい場合は、QuestPDF の導入を再検討する。

## 7. 技術構成案

### 7.1 MVP

- アプリケーション: ASP.NET Core Razor Pages
- プロジェクト構成: 既存の `dxpmt/dxpmt` 単一プロジェクトを維持
- DB: SQL Server LocalDB または SQL Server Express
- ORM: EF Core
- UI: Bootstrap
- 認証: DBログインを最小実装。社内運用時にWindows認証を追加
- 配備: IIS

単一プロジェクト内に次のフォルダを置く。

```text
Data/
Domain/
Services/
Pages/Cases/
Pages/Forms/
Pages/ActionItems/
Pages/Decisions/
Pages/Requirements/
```

`参考` のような Domain / Application / Infrastructure 分割は、初期MVPでは採用しない。機能が増え、複数人保守や外部連携が必要になった時点で分割を検討する。

### 7.2 将来拡張

- SQL Server 本番DB化
- Windows認証またはAD連携
- 添付ファイルのNAS保存
- Markdown / CSV / PDF 出力
- 版管理履歴の強化
- 案件テンプレート、フォーム定義のDB管理
- 通知、メール、Teams連携

## 8. 実装順

### フェーズ1: 骨格

1. レイアウトを日本語業務アプリ向けに変更する。
2. `Cases`、`CaseForms`、`GateReviews`、`ActionItems`、`DecisionRecords` を作る。
3. 案件一覧、案件詳細、F01/F02入力、課題、意思決定を作る。
4. ステータス変更とG0/G1判定を作る。

### フェーズ2: 調査・分析

1. F03 作業ヒアリング票を作る。
2. F04 業務フロー整理票を作る。
3. F05 問題・課題一覧を作る。
4. As-Is作業と問題の追跡リンクを作る。

### フェーズ3: 改善案・要求事項

1. F06 改善案評価票を作る。
2. F07 To-Be作業定義票を作る。
3. F08 要求事項一覧を作る。
4. 問題、改善案、To-Be、要求事項の追跡ビューを作る。
5. G3からG5のゲート判定を作る。

### フェーズ4: 効果確認・運用

1. F09 効果確認票を作る。
2. G6案件終結を作る。
3. 案件別Markdown/CSVエクスポートを作る。
4. 認証、権限、バックアップ、配備手順を整える。

## 9. MVPで決めるべきこと

実装前に、次の点だけ確認したい。

|論点|推奨|
|---|---|
|利用人数|まずは10から30名程度を想定|
|認証|初期はDBログイン、社内公開時にWindows認証を追加|
|DB|開発はLocalDB、本番はSQL Server Express以上|
|添付ファイル|DBではなくファイル保存。DBにはパスとメタ情報のみ|
|承認|厳密な多段承認ではなく、ゲート判断者の記録から開始|
|帳票出力|初期は画面表示とCSV/Markdown出力。PDFは後回し|
|フォーム定義|初期はコード定義。頻繁に変わる場合だけDB定義化|

## 10. リスクと対応

|リスク|対応|
|---|---|
|帳票項目をすべて正規化して初期開発が重くなる|JSON保存と主要項目列のハイブリッドで始める|
|ワークフローが現場で変わる|フォーム定義とステータス定数を集中管理する|
|実運用前のため、手順や帳票が大きく変わる|MVPでは変更しやすさを優先し、短いサイクルで画面を触って直す|
|探索開発のため、一部の手戻りや軽微なバグが発生する|致命的なデータ破損を防ぐ最小限の制約とバックアップを優先し、UIや項目は反復改善する|
|入力だけされて判断履歴が残らない|ゲート判定と意思決定記録を案件詳細から常に追加できるようにする|
|要求事項の出所が追えなくなる|TraceLinks を最初から入れる|
|参考システムの機能を入れすぎる|認証、DB、画面作法、配備だけに限定して流用する|

## 11. 推奨する次アクション

まずフェーズ1を実装し、1件のサンプル案件を最初からG1まで通せる状態にする。

最初の実装対象は次の順がよい。

1. 案件一覧・詳細
2. F01 案件受付票
3. F02 調査計画票
4. 課題・宿題
5. 意思決定記録
6. G0/G1ゲート判定

ここまでできれば、運用担当者が画面を触りながら「この項目は多い」「これは一覧で見たい」「ここは承認が必要」と具体的に判断できる。
